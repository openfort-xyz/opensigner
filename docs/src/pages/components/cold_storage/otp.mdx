# OTP for automatic recovery

Shield supports One-Time Password (OTP) verification to add an additional layer of security when creating encrypted sessions.

:::info
OTP is available only for shares with automatic recovery method.
:::

## Enable OTP

OTP is a project-level feature that must be enabled before it can be used. Once enabled, **OTP cannot be disabled** for a project.

To enable OTP for a project, use the following endpoint:

**Endpoint:** `POST /project/enable-2fa`

**Headers:**
- `X-API-Key`: Project's API key
- `X-API-Secret`: Project's API secret

**Response:**
- `200 OK`: OTP enabled successfully
- `409 Conflict`: OTP already enabled for this project

## How OTP works

On a 2FA project, users verify an OTP to recover or update a project-encrypted share. For wallet signup, the project backend can request a one-time session that can only register a share.

### 1. Request OTP

Request an OTP from your project backend. Use the project API secret on the backend.

**Endpoint:** `POST /project/otp`

**Headers:**
- `X-API-Key`: Project's API key
- `X-API-Secret`: Project's API secret

**Request Body:**
```json
{
  "user_id": "user_external_id",
  "email": "user@example.com",
  "dangerously_skip_verification": false
}
```

**OR**

```json
{
  "user_id": "user_external_id",
  "phone": "+1234567890",
  "dangerously_skip_verification": false
}
```

**Parameters:**
- `user_id` (required): The external user ID
- `auth_provider`: Use `custom` or `openfort` when more than one provider is configured. Use the same provider for the OTP request and session creation.
- `email` (optional): User's email address to receive OTP via email
- `phone` (optional): User's phone number to receive OTP via SMS
- `dangerously_skip_verification` (optional, default: `false`): Set to `true` to request a signup session without sending an OTP.

For OTP delivery, send exactly one of `email` or `phone`. For signup without an OTP, omit both contact fields.

**Response:**
- `200 OK`: Shield sent the OTP or accepted the signup request.

### 2. Create an encryption session

For an OTP-verified session, send the code the user received. For a signup session, omit `otp_code`.

**Endpoint:** `POST /project/encryption-session`

**Headers:**
- `X-API-Key`: Project's API key
- `X-API-Secret`: Project's API secret

**Request Body:**
```json
{
  "encryption_part": "encryption_part_value",
  "user_id": "user_external_id",
  "otp_code": "123456789"
}
```

**Parameters:**
- `encryption_part` (required): The encryption part for the project
- `user_id` (required): The external user ID
- `auth_provider`: Use `custom` or `openfort` when more than one provider is configured. Use the same provider for the OTP request and session creation.
- `otp_code` (optional): The OTP code received via email or SMS. Required if `dangerously_skip_verification` was `false`

**Response:**
```json
{
  "session_id": "generated_session_id"
}
```

### 3. Use the session

Use these session types for project-encrypted shares on a 2FA project.

| Operation | Where to send the session ID | Accepted session |
|-----------|------------------------------|------------------|
| Register a share with `POST /shares` | `encryption_session` in the JSON body | OTP-verified or signup |
| Write a share with project encryption using `PUT /shares` | `encryption_session` in the JSON body | OTP-verified |
| Switch an existing share from project encryption using `PUT /shares` | `X-Encryption-Session` header | Approval from the verified read of that share |
| Retrieve a share with `GET /shares` | `X-Encryption-Session` header | OTP-verified |

:::info
The write requirements apply to Shield versions that support signup-only sessions. Shield v0.5.4 and earlier accept a raw encryption part for share writes.
:::

Shield returns `428 OTP_MISSING` when a 2FA user sends a raw encryption part in place of a session or uses a signup session for a read or update.

## Change recovery methods

Read the project-encrypted share with an OTP-verified session before switching to password or passkey recovery. Shield consumes the read session and records a separate approval for that share version and user. Send the same session ID in the `X-Encryption-Session` header of the update within one minute. The approval works once. If the share changed since the read, start again with a new session.

## OTP security features

- **OTP Verification**: When OTP is enabled and `dangerously_skip_verification` is `false`, users must provide a valid OTP code to create an encrypted session
- **Contact Verification**: Shield verifies and stores hashed contact information (email or phone) to ensure consistency across requests
- **Rate Limiting**: Project-level rate limits prevent abuse of OTP generation
- **Session Expiry**: Encryption sessions are time-limited for security
- **Session Binding**: An encryption session works once for its project, authentication provider, and user

## Example workflows

### New user signup (skip verification)

1. Call `POST /project/otp` with the external `user_id` and `dangerously_skip_verification: true`. Omit `email` and `phone`.
2. Call `POST /project/encryption-session` with the same `user_id` and the `encryption_part`. Omit `otp_code`.
3. Pass the returned `session_id` to the iframe as `encryptionSession`. If you call `POST /shares` directly, send it as `encryption_session` in the JSON body.

### Existing user recovery (with verification)

1. Call `POST /project/otp` with the external `user_id` and an email address or phone number.
2. Ask the user for the OTP they receive.
3. Call `POST /project/encryption-session` with the same `user_id`, the `encryption_part`, and the `otp_code`.
4. Pass the returned `session_id` to the iframe as `encryptionSession`. If you call `GET /shares` directly, send it in the `X-Encryption-Session` header.

## OTP errors

| HTTP Status | Error Code | Message |
|-------------|------------|---------|
| 429 | `OTP_RATE_LIMIT` | Rate limit exceeded to generate OTP |
| 422 | `OTP_EXPIRED` | OTP is expired |
| 400 | `OTP_INVALIDATED` | OTP invalidated after max failed attempts |
| 400 | `OTP_INVALID` | Received otp is invalid |
| 400 | `OTP_REQUESTED_BUT_NOT_SENT` | OTP was requested but not sent |
| 428 | `OTP_MISSING` | OTP is required for this request |
| 404 | `OTP_RECORD_NOT_FOUND` | OTP record not found for user |
| 400 | `OTP_USER_INFO_MISSING` | Missing user information like email or phone number |
| 400 | `OTP_NOT_SUPPORTED` | Project doesn't support OTP |
| 409 | `OTP_ALREADY_ENABLED` | Project already has OTP enabled |

OTP verification follows the standard one-time password schemes, [HOTP (RFC 4226)](https://datatracker.ietf.org/doc/html/rfc4226) and [TOTP (RFC 6238)](https://datatracker.ietf.org/doc/html/rfc6238).
